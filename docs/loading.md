# Transactional target loading

Create an empty development database with the matching schema, then:

```sh
stuntdb load slice.sql --target "$STUNTDB_TARGET"
# An alternate receipt path:
stuntdb load slice.sql --target "$STUNTDB_TARGET" --manifest receipt.json
```

The default manifest is `slice.sql.manifest.json`. The loader validates the exact file bytes, header, supported insert syntax and per-table insert counts before connecting. Only the current stuntdb export format is accepted: literals and the narrow hex/spatial conversion expressions generated by the exporter. It rejects arbitrary SQL, DDL, extra commits and user-edited expressions. The loader controls transaction boundaries and foreign-key settings itself. A checksum is not a signature; use exports and manifests from a trusted source.

The target must have the same dialect, scoped schema signature and table set, with every reflected table empty, including tables receiving no rows. The loader never creates schemas, truncates tables or merges existing data. MySQL 8.0/8.4 and MariaDB 10.11/11.4 targets require InnoDB for all base tables. MySQL, MariaDB and SQLite targets with triggers are rejected because triggers can change rows or introduce side effects. Server-family compatibility is documented in [MariaDB support](mariadb.md). Views and every DDL/index/collation option are not covered by the scoped schema signature; see [verification](verification.md).

Foreign-key enforcement is temporarily disabled on the loading connection to allow cycles. Inserts, post-load row-count checks and declared-FK verification run inside one transaction. An insert or validation failure rolls back the imported rows. Session foreign-key settings are restored on success and failure. MySQL uses serializable isolation, strict insert mode and rejects insert warnings; its previous SQL mode is restored. SQLite uses an immediate transaction to exclude concurrent writers. Use a dedicated target during loading and do not change its schema concurrently. Database rollback does not rewind MySQL auto-increment counters.

The loader reads the SQL file and restored rows into memory. It checks storage/schema compatibility and declared relationships, not application semantics or arbitrary privacy. It does not rerun source-value leak detection; run `stuntdb verify` with a stable reference source and seed when needed. Unsupported legacy or manually rewritten SQL must be regenerated with snapshot.

Exit code 0 means the import committed after verification. Code 3 means checksum, schema, nonempty-target or integrity failure; code 1 means invalid format, connection, unsupported target or insert failure. Errors omit database exception details so credentials and row values are not printed. A lost connection during commit can leave the outcome uncertain; verify the target before retrying. Repeated loads into a populated target fail rather than duplicating data.
