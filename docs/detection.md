# Sample-based detection

`stuntdb init SOURCE` now samples locally to find sensitive-looking values in columns with uninformative names. Use `--sample-rows N` (default 100, maximum 1,000) to set the per-table bound. `--sample-rows 0` reads schema only and omits detection metadata. Initialization uses the same consistent read-only source transaction as snapshots.

Global limits are 1,000 returned rows, 10,000 returned cells and 513 characters per cell. Eligible strings and integers/fixed decimals are cast and truncated by the database before being returned. Enum/SET, JSON, binary, floating-point, Boolean, computed and spatial columns are excluded. Tables are visited alphabetically; primary keys order the sample where present. Limits can leave later tables or columns unsampled. LIMIT bounds returned data; it is not a database execution-time guarantee. The sample is neither random nor representative.

The config's `detection.findings` records only column names, format categories, suggested actions, confidence and fixed reasons. Sampled values are never added to configs, command output, manifests or application logs. No external detector, model or service receives them. Existing config files remain protected against overwrite.

At least three nonempty values, all fully within the character bound and matching only one format, suggest `email` or `phone`. Phone recognition requires formatting or an international `+` marker; bare digit strings are ambiguous identifiers. A small sample, mixed formats, embedded emails, SSN-shaped strings, valid IP literals and Luhn-matching card-shaped strings produce `review`, blocking snapshots when those columns' tables or linked domains are selected. Existing unsupported-type review rules are never relaxed. Numeric storage always requires review. No name, birth-date, address or arbitrary free-text inference is attempted from values.

“High” confidence means homogeneous sampled format, not a calibrated probability or a privacy guarantee. Credit-card checks identify a shape/checksum, not a real card; SSN detection does not validate issuance. False positives and false negatives are expected. Missing findings do not mean a column is safe, and values outside the sample can still make a suggested provider fail. Review all rules before snapshotting. Linked columns may need their explicit actions aligned; existing relationship-domain conflict checks remain active.

Changing a rule after review does not require deleting detection findings: they are advisory metadata, while `rules` alone controls masking. Name-based suggestions continue to apply to columns without sample findings. The existing leak check remains independent of sampling and still runs over the selected slice's transformed source values.
